# 2026-09-24 — карантин и Celery-публикация фото

## Context

PR #11 дал функции очистки изображения, но их никто не вызывал. Endpoint
загрузки нельзя открывать, пока исходник может оказаться в публичном storage.

## What

- `STORAGES["quarantine"]`: в dev — `quarantine/` вне `MEDIA_ROOT`, в тестах —
  in-memory, в production — отдельный приватный S3-бакет.
- `SightingPhoto`: `original` в карантине, `status`, `sha256`, `exif_geog`;
  `image` пуст до публикации. Миграция `sightings/0002`.
- `apps/sightings/services.py`: `accept_sighting_photo` кладёт исходник под
  UUID-именем и ставит задачу после коммита; `publish_sighting_photo`
  перекодирует, пишет точку из EXIF и удаляет исходник.
- Админка: фото отметки только для просмотра, без исходника и точки EXIF.
- Инвариантные тесты 4 (исходник не переживает карантин) и 11 (обработка не в
  запросе), расширен 6 (`exif_geog` — geography с GiST).

## Why

- **Отдельный бакет, а не префикс.** Ошибку в политике префикса снаружи не
  видно; приватный бакет целиком проверяется одной настройкой.
- **Хранилище — callable `apps.core.storage.quarantine_storage`.** Иначе
  миграция зафиксировала бы бэкенд окружения, где её сгенерировали.
- **Удаление исходника — `on_commit`.** Если транзакция откатится, фото
  останется `pending` с файлом и задачу можно перезапустить.
- **`select_for_update` + фильтр по `pending`.** Celery может доставить задачу
  дважды; второй запуск не создаёт вторую копию.
- **Точка EXIF — поле фото, а не отметки.** Автопозиционирование отметки по
  ней — отдельное продуктовое решение; сейчас точка только сохраняется.
- **Админка без загрузки.** Прямая загрузка в `image` обошла бы очистку, то есть
  нарушила бы инвариант 4 руками модератора.
